## Project name
Precedent

## Elevator pitch
Before you ship, know what happened last time. Precedent brings prior Jira incidents, Confluence decisions and explainable ship confidence into the issue you are reviewing.

## Category
Apps for Software Teams

## Inspiration
Teams can re-litigate decisions when the reasoning is buried in old tickets or
pages that are hard to discover. Repeated incidents become more likely when that
context is missing from the next change. I built Precedent to put prior decisions
and incident evidence next to the work, before the release conversation happens.

## What it does
Precedent adds an issue panel to Jira. It finds similar resolved work, relevant
Confluence decision pages and people who worked on earlier issues. It explains
a deterministic ship-confidence score factor by factor, with inspectable evidence.
The score starts a conversation; it does not approve a release.

I can record a decision with its rationale, search it from a project ledger and
replace it without erasing the original. The same evidence and decision operations
are available to a Rovo agent and as four tools through Atlassian MCP.

My demo follows a payments team adding retries for card authorization timeouts.
The panel connects that change to a double-charge incident and an idempotency ADR.

## How I built it
I built Precedent on Atlassian Forge with Node.js functions, Jira and Confluence
REST APIs, Forge KVS and two React Custom UI surfaces. The interface uses Atlassian
design tokens and follows the host's light or dark theme.

I extract keywords from the current issue, search resolved Jira work and Confluence
decision pages, then calculate explicit risk factors in JavaScript. Product reads
run as the current user. Decisions stay in Forge KVS rather than an external service.

I declared a `rovo:agent`, four actions and a `rovo:mcp` module in the manifest.
I also consume the Teamwork Graph assigned-work curated query as optional context.
I use Vitest for backend, form, ledger and seed-plan coverage, plus Playwright
for screenshot and interaction checks.

## Challenges I ran into
I wanted useful context without pretending that a score predicts release safety.
I made each factor deterministic and visible, and kept missing-data warnings in
the interface. I also needed to preserve Jira permissions when returning stored
decisions, not just when fetching issues.

Forge CLI linting requires authentication, so I added an offline manifest-schema
check for local development. Preview integrations can be unavailable on a site;
I kept Graph enrichment optional so core Jira and ledger evidence still works.

## Accomplishments I am proud of
I connected the release question, historical evidence and a durable decision record
in one workflow. I made the interface usable in both Jira themes and kept the
same backend operations available to the panel, Rovo and MCP clients. I also built
a repeatable payments demo plan instead of depending on manually staged tickets.

## What I learned
Keeping evidence permission-aware is as important as finding it. A missing
integration is different from missing evidence, and that distinction needs to be
visible. A useful agent needs clear write boundaries and source links, not just
a fluent answer. These principles shape my implementation.

## What's next
I want to validate the score with real teams, improve relevance beyond keyword
overlap, add scalable indexed ledger search, and support richer relationships
between decisions and releases. I would also add stronger project-level controls
for unlinked decisions and validate more site workflow configurations.

## Bonus: Best Agents
I included `rovo:agent` with three conversation starters and four actions:
`get-issue-precedent`, `assess-ship-readiness`, `search-decisions` and
`record-decision`. The agent is instructed to retrieve evidence before answering,
cite sources, state missing information and ask for explicit confirmation before
recording. The score itself is deterministic, not generated by a model.

## Bonus: Best app with Atlassian MCP
I expose the same four actions through `rovo:mcp` (Preview). A judge can install
the app, then have a site/org admin open **Atlassian Administration → Apps → Sites
→ their site → Connected apps → Precedent**, open the app details and enable the
tools for external MCP. Exposure is disabled by default and is set per installation.

In a remote-MCP-compatible client, add `https://mcp.atlassian.com/forge/<appId>`.
Here `<appId>` is the UUID portion of my registered Forge app ID, not its full ARI:
the actual endpoint is `https://mcp.atlassian.com/forge/<APP_UUID>`. Complete the
OAuth 2.1 flow, select the installed site and consent to the tools. Ask the client
to assess the seeded target issue using its actual key. User permissions still apply.

I provide an open-source agent guide at `skills/precedent/SKILL.md` under CC0-1.0
so third-party agents can use the tools with explicit write confirmation.
[Current MCP setup documentation](https://developer.atlassian.com/platform/forge/manifest-reference/modules/rovo-mcp/).

## Bonus: Teamwork Graph integration
I consume `atlassianUserAssignedJiraWorkItems(userId: ..., first: 25)` through
`api.asUser().requestTeamworkGraph()`. I start from the current issue's assignee
and request Jira work-item IDs and titles. These appear as additional work context,
not as an input to the confidence score. I do not publish data into the Graph.

Teamwork Graph is Preview. No assignee, missing grants, empty results or an API
failure produces a warning and leaves Jira, Confluence and ledger evidence usable.
I do not claim this optional enrichment is available in every judge environment.
[Curated query documentation](https://developer.atlassian.com/platform/teamwork-graph/curated-queries/).

## Testing instructions for judges
1. As a site admin, install from **<INSTALL_LINK>** on a site with Jira and
   Confluence; install/consent on both products. A Rovo-enabled site is needed
   for the agent segment. Regular Jira evidence and the ledger do not require MCP.
2. On a disposable site, an admin can run `node scripts/seed-demo.mjs --dry-run`,
   then set `ATLASSIAN_SITE`, `ATLASSIAN_EMAIL`, `ATLASSIAN_API_TOKEN` and run
   `node scripts/seed-demo.mjs`. Optional `PROJECT_KEY` and `SPACE_KEY` default
   to PAY. The script prints the target URL. Jira allocates its key; use that key
   rather than assuming PAY-412.
3. Without the script, create three resolved Bug issues about payment authorization
   retries, mark two with `incident`, and ensure each has a resolution. Create an
   open Task for gateway reconciliation and an open retry Task with acceptance
   criteria; make the former block the latter. Create a Confluence page titled
   “ADR-007 · Idempotency keys for payment retries”, labeled `adr` and `decision`,
   containing “authorization retry timeouts checkout gateway idempotency”.
4. Open the retry issue → **Precedent**. Allow first-use authorization. Expand the
   blocker and past-failure factors, follow a precedent, and inspect the ADR.
   Allow time for Jira/Confluence indexing after seeding.
5. Choose **Record decision**. Title: “Use one idempotency key across authorization
   retries”. Decision: “Reuse the checkout idempotency key on every retry”.
   Rationale: “A timeout is not a failed authorization; a fresh key can double charge”.
   Save. On a clean seed the score changes from 67 to 72, both Caution.
6. Open the project's **Decision Ledger** page, search “idempotency”, select a
   decision and inspect its rationale. To test superseding, record a second
   accepted decision, open the first as its author and choose **Supersede decision**.
   The original stays in history. Do not supersede before checking the baseline score.
7. Open Rovo Chat, choose **Precedent**, use “Assess this issue's ship readiness”
   and include the actual target key. Try the other conversation starters. For
   recording, confirm the exact text before allowing the write action.
8. For external MCP, follow the bonus setup above. Add the supplied skill to the
   client's instructions and request evidence for the same explicit issue key.
   If Graph or MCP is unavailable, inspect the warning; do not interpret it as a
   successful integration call.
